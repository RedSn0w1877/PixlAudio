# Song Tap, Android, milestones 1 and 2 (2026-11-20)

Branch `song-tap` (from `origin/music-brain`). Not pushed. Milestone 1 is the pure core, the QR route, the
receiver's save and undo, the settings and a plain working screen. Milestone 2 (the second half of this file,
"Milestone 2") is the Bluetooth tap, the beam animation, Developer mode diagnostics and the Bluetooth permission.
Milestone 2 changed the core (a Bluetooth wire format, spec version 2): the iOS port must re-copy the goldens.

Song Tap sends the song that is playing to another phone with PixlAudio and adds it to that phone's library.
Only a few ids and the text travel (at most 400 bytes); each phone streams the audio itself.

## What is in it

### `:songtap` (new Kotlin JVM module, copied from `:brain`'s build setup)

Pure: standard library only, integers only (no `Double`/`Float`), no clock, no randomness, no crypto, no I/O.
`PurityTest` bans platform imports and calls, floating point and locale-dependent text calls.

| File | What it is |
|---|---|
| `SongTapText.kt` | strict UTF-8, the characters a beam may never carry (controls, zero width, bidi, tags, noncharacters), `sanitize` (idempotent) |
| `SongTapPayload.kt` | `SongTapPayload`, canonical encode, strict decode (accepts exactly what encode writes), `make` (builds one from raw song data, drops optional parts until it fits 400 bytes), id and art URL validators |
| `SongTapLink.kt` | `pixlsong1:` + base64url (no padding, unique form) for the QR code |
| `SongTapSigning.kt` | `signingBytes` = payload, challenge (16), timestamp (8, big endian); the signed-offer frame; `check` with an injected `SongTapSignatureVerifier`; windows (30 s offer, 5 min QR); `senderKey` |
| `SongTapSession.kt` | the state machine `reduce(state, event) -> (state, effects)`: IDLE, ARMED, FOUND, NEAR, OFFERED, TRANSFERRING, SAVED, DECLINED, FAILED, CANCELLED |
| `SongTapRateLimits.kt` | 1 accepted beam per 3 s, 10 a minute, 30 an hour, same video not twice in 60 s, two undos mute a sender for an hour |

## Behaviour

- Off by default. Turn it on from Settings > Song Tap or the "Turn on Song Tap" button on the screen. The player's
  menu has a "Song Tap" row (third in the Listen group, shows On / Off) that opens the screen.
- Armed only while the screen is resumed (`LifecycleResumeEffect`): leaving the screen or the app disarms, stops
  the camera and cancels every timer. Nothing runs at app start.
- Send: shows the playing song and a code (QR). The code is remade every 4 minutes (it is good for 5).
- Receive: the camera reads a code. The first beam ever asks (Add / Not now); once the listener says yes, later beams
  save at once and show Undo for 6 s. Already in the library says so and has no Undo. A song that cannot be found
  says "Couldn't find this one here" and saves nothing.
- Haptics: the controller emits cues (`TICK` on the offer, `SUCCESS` on a save, `WARN` on a failure); the screen
  performs them through `performAppHapticFeedback`, so the Haptics setting is respected.

## Deviations from the research reports (the code won)

1. Payload `yt` is optional (at least one of `yt` and `sp` is required). A Spotify song that was never played has no
   matched video, so it can only be beamed by its Spotify id and the receiver finds the video with the app's own
   search and scoring. The reports listed the video id as required.
2. QR carries the payload unsigned: nothing travels back, so there is no challenge to sign and a signature that
   travels with the key proves nothing. Freshness is the limit (5 minutes, the sender remakes the code every 4), plus
   the rate limits and the strict payload rules. Signing, the challenge and the frame are built, tested and
   ready for the Bluetooth route.
3. No `PlayableStore.register`: `importYouTubeMusicTracks` writes a MATCHED row (`matchedVideoId` set) and
   `SpotifyStreamProxy` resolves `spotifyDao.getMatchedVideoId` first, so the song plays at once. Registering
   would also need a brain `rid`, which would put a beamed song into the brain's recording tables.
4. Undo uses `SpotifyRepository.removeFromExploredCatalog` (found, not written): it removes the song only when it
   belongs to the "Saved from Spotify" browse playlist alone, which is exactly what a beam adds. If the listener adds
   it to a playlist inside the 6 seconds, Undo does nothing (the card does not say so yet).
5. "Already in the library" needed one new read-only query, `SpotifyDao.getSpotifyIdForVideo`, because a song synced
   from the listener's real Spotify sits under its real id, not the made-up one.
6. The player-menu row opens the screen through `SheetActionHandlers` (the same place "go to artist" navigates from),
   not through `PlayerMenuRequest`, because the song options sheet has no navigation handle and the enum is only
   handled inside the full player. `PlayerExtrasLocals.kt` is untouched.
7. Private session needs no switch on the receiving side: the receiver only touches the library (a test pins its
   constructor to the library port), never the listening tracker or `EngineTrackSaver`, so no listening event and no
   saved-during flag can be written.
8. The sender key is the last 4 bytes of the signer's public key. The key is ephemeral per session, so "two undos mute
   that sender for an hour" holds for that session's key; a sender that re-arms is a new key. There is nothing better
   to key on without a stable identifier, which the privacy rules rule out. A QR beam carries no key (0), so nobody is muted for it
   (muting would silence every code on the table); only the rate limits apply.
9. The signed-offer frame is capped at 512 bytes (one GATT attribute); a payload close to 400 bytes plus the key and
   signature (150 bytes) can exceed it, in which case the controller must remake the payload without art.
   Typical payloads are 200 to 300 bytes.
10. Haptics use the `View` constants (CLOCK_TICK, CONTEXT_CLICK, CONFIRM, REJECT) in this milestone, not
    `VibrationEffect` compositions.

## For the iOS port

Port `:songtap` file for file into `Packages/PixlCore/Sources/PixlLibrary/SongTap/` with the same names and copy
`songtap/src/test/resources/songtap-golden/` byte for byte to `Tests/PixlLibraryTests/Fixtures/songtap/`
(`MANIFEST.sha256` lists the hashes). The README in that folder says how to replay every `fn`.

- Work on unicode scalars, not Swift `Character`s: `sanitize` and the byte caps count scalars and UTF-8 bytes.
- Integer arithmetic only. Division truncates toward zero in both languages; the only floor division is
  `SongTapDetector.floorDiv`. `shr` on Int is an arithmetic shift (Swift `>>` on `Int` is too).
- Payload JSON is written by hand with the fixed key order (`v, ts, yt, sp, isrc, t, a, d, art`), `ts` as a plain
  integer; decoding must re-encode and compare bytes (that is what makes "accepted" mean "canonical").
- Events in `session.jsonl` are the strings `SessionEvent.describe()` prints: `name(arg,arg)`, roles `send`/`receive`,
  `-` for an empty video id.
- Crypto: `P256.Signing` with SHA-256; public key `x963Representation` (65 bytes), signature `rawRepresentation`
  (64 bytes). The signed message is `signingBytes` (goldens cover it; never a signature).
- The iOS UI must not say "Apple" and uses Liquid Glass only (see the spec); the timeline frames are the same numbers.

## How to test with two phones

Needs two phones with this build (two Androids, or this one and the iPhone once the iOS port reads `pixlsong1:`
links). The QR route needs no radio and no internet for the code itself; saving needs the network (the song is
matched to a video and its metadata is stored).

1. Both phones: Settings > Song Tap > Allow Song Tap (or open the screen and press Turn on Song Tap).
2. Phone A: play a Spotify song, open the player's three-dot menu, tap Song Tap. Pick Send, tap Show code.
3. Phone B: open Song Tap, pick Receive, allow the camera, point it at A's screen.
4. Phone B first time: a card asks Add / Not now. Tap Add: "Added to your library" with Undo. Find the song in the
   library and play it.
5. Beam a second song: it saves at once. Tap Undo within 6 seconds: it is gone from the library.
6. Beam the same song again after a minute: "Already in your library".
7. Beam twice within 3 seconds, or the same song twice within a minute: the card says why not.
8. Hold up a QR code that is not Song Tap's: "That isn't a PixlAudio song code."
9. Play a song that was never played before (a Spotify song with no video yet) and send it: the receiver searches and
   saves the match, or says it couldn't find it.

## How a beam goes over Bluetooth

1. Both phones are armed (the screen is open and resumed). Each advertises ONE service UUID that names its role
   (`SERVICE_SEND` or `SERVICE_RECEIVE`) and scans for both. Nothing else is in the advertisement: no name, no data, no
   TX power. Android uses a private random address; the app treats no address as an identity.
2. Each phone follows the strongest other phone (another takes over only when 6 dB stronger and nothing is in flight).
   The approach glow is the smoothed signal of that phone. `PeerFound`, `PeerNear` and `PeerFar` come from the detector.
3. A receiver connects, as the GATT client, to the sender it is near (`near` means above -70 dBm smoothed, loose on
   purpose). It asks for MTU 517, finds the service, subscribes to Event and writes `Hello` with a fresh 16 byte challenge.
4. The detector fires on either path in `SongTapDetector` (a jump of at least 15 dB over the baseline held 150 ms with a
   jerk on either phone within 400 ms, or the jump held 400 ms). The receiver reads the sender's last-jerk age (Info) when
   the jump starts, so a jerk on the other phone counts. On a fire both phones announce the peer's role first, then the tap.
   A receiver also writes `Tap` to the sender; the sender takes that as its own tap only if its own signal jumped in the last 1.5 s.
5. Sender: `TapDetected` publishes the offer. Receiver: `TapDetected` reads Offer. The sender signs
   `payload || challenge || timestamp` on the read (ECDSA P-256, a new key per session); not-ready is the ATT error 0x80 and
   the receiver asks again every 250 ms, ten times at most.
6. The receiver checks frame, payload, freshness (30 s) and signature, then the session decides (first beam asks, rate
   limits), saves and writes `Ack`. A new challenge is written for the next beam whatever happened.
7. The sender answers `Ack` with Go (a notification on Event) and both animations start at T0 = go + 150 ms, the
   receiver's corrected by half the measured round trip of its Ack write.
8. The sender's beam is the whole send: when it ends the session is done. The receiver's card rests six seconds with Undo
   (the Undo chip is inside the beam, from 1.0 s to 7.0 s), then slides away and the session returns to waiting.

### The wire (for the iOS port)

`SongTapWire` in the core has every constant and message; `wire.jsonl` holds the goldens.

| | UUID (all lower case) | Properties | Value |
|---|---|---|---|
| send service | `b7f3a1c0-5d2e-4c9a-8e61-3f4d7a2b9c01` | advertised by a sending phone | |
| receive service | `b7f3a1c0-5d2e-4c9a-8e61-3f4d7a2b9c02` | advertised by a receiving phone | empty, no server |
| Info | `...9c11` | read | version 1, age of the sender's last jerk in ms, u32 big endian, `0xFFFFFFFF` none |
| Offer | `...9c12` | read | the signed frame (`SongTapSigning.encodeFrame`), at most 512 bytes; ATT error `0x80` until ready |
| Control | `...9c13` | write | `01` Hello + 16 byte challenge, `02` Ack, `03` Decline, `04` Tap + age (u32) |
| Event | `...9c14` | notify | `01` Go |

On iOS: the sender is a `CBPeripheralManager` with that service and four characteristics (an Offer read must be answered
from `didReceiveRead`, with the value for the current challenge, and with `0x80` as the error code when there is none); the receiver is a
`CBCentralManager` that scans for both UUIDs (`allowDuplicates: true`, RSSI from `didDiscover`), connects, discovers, sets notify on Event.
Android's long read is handled (the first read signs, later offsets reuse that value). Sign with `P256.Signing`, public key
`x963Representation`, signature `rawRepresentation`.

## Deviations from the research reports and the brief (milestone 2)

11. **Two service UUIDs, one per role, instead of one.** A phone still advertises exactly one, but which one tells the
    other its role without a connection, which is what makes "both sending" and "both receiving" known from the scan alone.
    The brief's "one UUID" would need a connection first.
12. **The receiver is always the GATT client, the sender the server.** The brief had the receiver expose the challenge and
    the sender read it, which needs two connections in opposite directions. Here the receiver writes the challenge into
    the sender's Control and reads Offer; one connection, one direction. Same security: the signature covers the receiver's
    challenge and the time.
13. **The sender signs when the receiver reads**, not when the tap fires, so the challenge is the receiver's current one. The
    ATT error 0x80 plus a short retry covers the sender being a few milliseconds behind.
14. **A receiver's `Tap` message can be the sender's tap** (when the sender's own signal jumped in the last 1.5 s). The brief
    had both phones detect on their own; with two different antennas one phone can miss. `BleTuning.PEER_TAP_JUMP_WINDOW_MS`.
15. **Peer jerk is read on demand**: the receiver reads Info when the jump starts (the sender's jerk age), instead of both
    phones exchanging impulse times in a handshake before the tap. A sender cannot see the receiver's jerk until the receiver
    writes `Tap`, which carries it.
16. **Only the first phone near is connected**, and a connection that has not been near for 4 s is closed. A phone leaving
    in the middle of a beam is a lost peer.
17. **The Bluetooth permission is asked by the "Turn on Song Tap" button on the screen** (that is where the player menu row
    leads), and again by one button on the screen if it was refused. No setup page.
18. **The accelerometer runs at 50 readings a second** while armed (no batching), the lowest rate the core's jerk rule was
    written for. It allocates three small objects per reading; nothing of ours allocates per frame in the beam.
19. **`frameInto`/`BeamFrameBuffer` added to the core** so the draw loop allocates nothing per frame. The compose runtime's own
    per-frame work (the `Animatable`) is not counted.
20. **The consent card and the beam are separate**: the first beam's Add / Not now is the plain card; after Add the beam's card
    enters. After the first beam a receiver sees only the beam.

## Known risks to look at first on the phones

- **A slow approach can still read as a tap if it ends very close.** (Reduced in the review pass, see below: the dwell path now
  needs the smoothed signal at -58 dBm or stronger, a held jump that has not fired after 2 s is taken as the new level, and the
  baseline catches up after every fire.) A phone brought to a few centimetres over a second or two can still fire the dwell path
  without a knock. Look at "jump" and "held for" in the diagnostics while bringing the phones together slowly and move
  `DWELL_MIN_DBM` or drop the dwell path. All in `SongTapTuning`; golden change if edited.
- **`NEAR_ENTER_DBM` (-70) is a guess** for "within about a metre": it only decides when a receiver connects.
- **The two timeouts** (fixed in the review pass): a sender now waits 45 s for an answer, longer than the receiver's 20 s consent and
  20 s save together.
- A sender that is playing but whose song has no Spotify id cannot send (as in milestone 1).

## How to test Bluetooth with two phones

Needs two Android phones with this build (the iPhone after the iOS port reads the same wire), Bluetooth on, both signed in
to Spotify, a song with a Spotify id playing on one.

1. Both: Settings > Song Tap > on (or the Song Tap row in the player menu, then "Turn on Song Tap") and allow Bluetooth.
2. Developer mode on, both phones: Settings > Song Tap > Song Tap diagnostics. Set one to Send, one to Receive. Hold them
   30 cm apart and press "30 cm", then 10, 3, 1 and touching: "Copy log" has the numbers. Tap them together a few times and
   read "jump", "held for" and "last tap" on both. This is how the thresholds get calibrated.
3. Phone A: play a song, open Song Tap, Send. Phone B: open Song Tap, Receive. Bring B's back to A's back slowly: the glow at
   the top of each screen grows, the status line says "Phone nearby". Touch: both buzz once, the artwork leaves A through the
   top and B's card opens with the song and Undo. The song is in B's library and plays.
4. First beam on B asks Add / Not now. Not now: A says "Not added". Beam again: Add, and from then on it saves by itself.
5. Undo within six seconds removes it. The same song again within a minute says "You just got that one".
6. Both Send: both say "Both phones are sending. Switch one to Receive." Both Receive: nothing happens.
7. Turn Bluetooth off during a beam: the sender and receiver recover to waiting, the screen says Bluetooth is off.
8. Developer settings > animator duration scale off: the beam cross-fades (no flight).
9. Leave the screen: scanning, advertising and the sensor stop (check Developer options > Bluetooth, or the diagnostics screen showing "idle").

## How to test with two phones (all four pairs)

Common: Bluetooth on both, both signed in to Spotify, Song Tap allowed (Settings > Song Tap, or the player menu row), a song
with a Spotify id playing on the sender. Developer mode on both for the diagnostics screen (Settings > Song Tap > Song Tap
diagnostics): hold the phones 30 / 10 / 3 / 1 cm and touching, press the mark buttons, "Copy log".

**Android with Android (Pixel and a second Android)**
1. A: Song Tap > Send. B: Song Tap > Receive. Bring the backs together slowly: glow grows on both, "Phone nearby".
2. Touch once. Both buzz, A's artwork leaves through the top, B's card opens, the song plays in B's library.
3. First beam on B asks Add / Not now. Pull the phones apart BEFORE pressing Add, then press Add: it still saves (finding 3).
4. Beam five songs in a row without asking: the sixth asks again. Undo within 6 s removes the song; the same song within a
   minute says "You just got that one".
5. Keep the phones together after a tap for 10 s: nothing fires again (finding 2).
6. Hold both phones 20 cm apart on a desk and slowly lower one onto the other: record what the diagnostics show for "jump" and
   "held for"; it should only fire on contact (finding 6).

**iOS with iOS** (after the iOS BLE transport lands): same as above; additionally lock one phone mid-beam and check that both
sides recover to waiting.

**Pixel with iPhone** (the pair that matters most)
1. Both on the build that speaks spec 3 (the wire is `wire.jsonl`; iOS must advertise one service, expose Info, Offer, Control and
   Event, and answer a read of the offer with the signed frame, 142 bytes of overhead, in one long read of up to 512 bytes).
2. Pixel Send, iPhone Receive and then the other way round. Look first at the diagnostics on both: the RSSI at contact differs per
   phone; the detector is relative, but `DWELL_MIN_DBM` (-58), `PEER_IMPULSE_MIN_DBM` (-62) and `NEAR_ENTER_DBM` (-70) are absolute
   and may need moving.
3. Check that the Pixel's Generic Access Device Name is not readable by a stranger (finding 13), with nRF Connect on a third phone.
4. If the iPhone's offer read comes back truncated, the frame is too long for its MTU: look at "offer refused" in the Android log.

**QR fallback (any pair, no radio)**
1. Sender: Song Tap > Send > Show code. Receiver: Receive, point the camera at it. Same card, same Undo; no partner animation.
2. While the code is up, skip to the next track on the sender: the code changes with the song (finding 9).
3. Scan a code of another song while the receiver's Add / Not now card is open: the card does not change (finding 4).
4. Scan a code that is not Song Tap's: "That isn't a PixlAudio song code."
