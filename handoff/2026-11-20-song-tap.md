# Song Tap, Android, milestone 1 (2026-11-20)

Branch `song-tap` (from `origin/music-brain`). Not pushed. Milestone 1 is the pure core, the QR route, the
receiver's save and undo, the settings and a plain working screen. Milestone 2 is the Bluetooth tap (the
detector is already in the core and tested), the animation, the diagnostics screen and the Bluetooth permission.

Song Tap sends the song that is playing to another phone with PixlAudio and adds it to that phone's library.
Only a few ids and the text travel (at most 400 bytes); each phone streams the audio itself.

## What is in it

### `:songtap` (new Kotlin JVM module, copied from `:brain`'s build setup)

Pure: standard library only, integers only (no `Double`/`Float`), no clock, no randomness, no crypto, no I/O.
`PurityTest` bans platform imports and calls, floating point and locale-dependent text calls.

| File | What it is |
|---|---|
| `SongTapText.kt` | strict UTF-8, the characters a beam may never carry (controls, zero width, bidi, tags, noncharacters), `sanitize` (idempotent) |
| `SongTapPayload.kt` | `SongTapPayload`, canonical encode, strict decode (accepts exactly what encode writes), `make` (builds one from raw song data, drops optional parts until it fits 400 bytes), id and art URL validators |
| `SongTapLink.kt` | `pixlsong1:` + base64url (no padding, unique form) for the QR code |
| `SongTapSigning.kt` | `signingBytes` = payload, challenge (16), timestamp (8, big endian); the signed-offer frame; `check` with an injected `SongTapSignatureVerifier`; windows (30 s offer, 5 min QR); `senderKey` |
| `SongTapSession.kt` | the state machine `reduce(state, event) -> (state, effects)`: IDLE, ARMED, FOUND, NEAR, OFFERED, TRANSFERRING, SAVED, DECLINED, FAILED, CANCELLED |
| `SongTapRateLimits.kt` | 1 accepted beam per 3 s, 10 a minute, 30 an hour, same video not twice in 60 s, two undos mute a sender for an hour |
| `SongTapDetector.kt` | the proximity detector (relative signal jump + jerk, or jump + dwell), every threshold in `SongTapTuning`; the accelerometer jerk detector |
| `SongTapTimeline.kt` | the animation as a pure function of time (`frame(role, tMs, reducedMotion)`, permille integers) and the haptic cue list |
| `SongTapHandshake.kt` | the clock alignment (`go` = now + 150 ms, receiver start = receipt + 150 ms - half the round trip) |

Tests (`./gradlew :songtap:test`): payload accept and reject lists, a 5000 round fuzz, state machine scenarios
(both-send, drop, duplicate, late event, cancel mid-transfer, timeouts, limits, mute), detector, timeline ranges,
signing bytes and frames, and `SongTapGoldenTest`.

Golden files: `./gradlew :songtap:generateGolden` writes `songtap/src/test/resources/songtap-golden/` (13 files,
`MANIFEST.sha256`, `SPEC_VERSION`, `README.md` saying how to replay each `fn`). `.gitattributes` keeps them LF.

## Behaviour

- Off by default. Turn it on from Settings > Song Tap or the "Turn on Song Tap" button on the screen. The player's
  menu has a "Song Tap" row (third in the Listen group, shows On / Off) that opens the screen.
- Armed only while the screen is resumed (`LifecycleResumeEffect`): leaving the screen or the app disarms, stops
  the camera and cancels every timer. Nothing runs at app start.
- Send: shows the playing song and a code (QR). The code is remade every 4 minutes (it is good for 5).
- Receive: the camera reads a code. The first beam ever asks (Add / Not now); once the listener says yes, later beams
  save at once and show Undo for 6 s. Already in the library says so and has no Undo. A song that cannot be found
  says "Couldn't find this one here" and saves nothing.
- Haptics: the controller emits cues (`TICK` on the offer, `SUCCESS` on a save, `WARN` on a failure); the screen
  performs them through `performAppHapticFeedback`, so the Haptics setting is respected.

## Deviations from the research reports (the code won)

1. Payload `yt` is optional (at least one of `yt` and `sp` is required). A Spotify song that was never played has no
   matched video, so it can only be beamed by its Spotify id and the receiver finds the video with the app's own
   search and scoring. The reports listed the video id as required.
2. QR carries the payload unsigned: nothing travels back, so there is no challenge to sign and a signature that
   travels with the key proves nothing. Freshness is the limit (5 minutes, the sender remakes the code every 4), plus
   the rate limits and the strict payload rules. Signing, the challenge and the frame are built, tested and
   ready for the Bluetooth route.
3. No `PlayableStore.register`: `importYouTubeMusicTracks` writes a MATCHED row (`matchedVideoId` set) and
   `SpotifyStreamProxy` resolves `spotifyDao.getMatchedVideoId` first, so the song plays at once. Registering
   would also need a brain `rid`, which would put a beamed song into the brain's recording tables.
4. Undo uses `SpotifyRepository.removeFromExploredCatalog` (found, not written): it removes the song only when it
   belongs to the "Saved from Spotify" browse playlist alone, which is exactly what a beam adds. If the listener adds
   it to a playlist inside the 6 seconds, Undo does nothing (the card does not say so yet).
5. "Already in the library" needed one new read-only query, `SpotifyDao.getSpotifyIdForVideo`, because a song synced
   from the listener's real Spotify sits under its real id, not the made-up one.
6. The player-menu row opens the screen through `SheetActionHandlers` (the same place "go to artist" navigates from),
   not through `PlayerMenuRequest`, because the song options sheet has no navigation handle and the enum is only
   handled inside the full player. `PlayerExtrasLocals.kt` is untouched.
7. Private session needs no switch on the receiving side: the receiver only touches the library (a test pins its
   constructor to the library port), never the listening tracker or `EngineTrackSaver`, so no listening event and no
   saved-during flag can be written.
8. The sender key is the last 4 bytes of the signer's public key. The key is ephemeral per session, so "two undos mute
   that sender for an hour" holds for that session's key; a sender that re-arms is a new key. There is nothing better
   to key on without a stable identifier, which the privacy rules rule out. A QR beam carries no key (0), so nobody is muted for it
   (muting would silence every code on the table); only the rate limits apply.
9. The signed-offer frame is capped at 512 bytes (one GATT attribute); a payload close to 400 bytes plus the key and
   signature (150 bytes) can exceed it, in which case the controller must remake the payload without art.
   Typical payloads are 200 to 300 bytes.
10. Haptics use the `View` constants (CLOCK_TICK, CONTEXT_CLICK, CONFIRM, REJECT) in this milestone, not
    `VibrationEffect` compositions.

## For the iOS port

Port `:songtap` file for file into `Packages/PixlCore/Sources/PixlLibrary/SongTap/` with the same names and copy
`songtap/src/test/resources/songtap-golden/` byte for byte to `Tests/PixlLibraryTests/Fixtures/songtap/`
(`MANIFEST.sha256` lists the hashes). The README in that folder says how to replay every `fn`.

- Work on unicode scalars, not Swift `Character`s: `sanitize` and the byte caps count scalars and UTF-8 bytes.
- Integer arithmetic only. Division truncates toward zero in both languages; the only floor division is
  `SongTapDetector.floorDiv`. `shr` on Int is an arithmetic shift (Swift `>>` on `Int` is too).
- Payload JSON is written by hand with the fixed key order (`v, ts, yt, sp, isrc, t, a, d, art`), `ts` as a plain
  integer; decoding must re-encode and compare bytes (that is what makes "accepted" mean "canonical").
- Events in `session.jsonl` are the strings `SessionEvent.describe()` prints: `name(arg,arg)`, roles `send`/`receive`,
  `-` for an empty video id.
- Crypto: `P256.Signing` with SHA-256; public key `x963Representation` (65 bytes), signature `rawRepresentation`
  (64 bytes). The signed message is `signingBytes` (goldens cover it; never a signature).
- The iOS UI must not say "Apple" and uses Liquid Glass only (see the spec); the timeline frames are the same numbers.

## How to test with two phones

Needs two phones with this build (two Androids, or this one and the iPhone once the iOS port reads `pixlsong1:`
links). The QR route needs no radio and no internet for the code itself; saving needs the network (the song is
matched to a video and its metadata is stored).

1. Both phones: Settings > Song Tap > Allow Song Tap (or open the screen and press Turn on Song Tap).
2. Phone A: play a Spotify song, open the player's three-dot menu, tap Song Tap. Pick Send, tap Show code.
3. Phone B: open Song Tap, pick Receive, allow the camera, point it at A's screen.
4. Phone B first time: a card asks Add / Not now. Tap Add: "Added to your library" with Undo. Find the song in the
   library and play it.
5. Beam a second song: it saves at once. Tap Undo within 6 seconds: it is gone from the library.
6. Beam the same song again after a minute: "Already in your library".
7. Beam twice within 3 seconds, or the same song twice within a minute: the card says why not.
8. Hold up a QR code that is not Song Tap's: "That isn't a PixlAudio song code."
9. Play a song that was never played before (a Spotify song with no video yet) and send it: the receiver searches and
   saves the match, or says it couldn't find it.
