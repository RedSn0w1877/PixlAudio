# Pixl ring code, Android (2026-11-21)

Branch `song-drop`, now merged into `everything`. R1 (the sections up to "R2" below) is the pure core and the scanner maths, in `:songtap`. R2 (the last section) puts the code on the Song Tap screen with the camera scanner and the Developer mode diagnostics. **Nothing here has run on a phone**: it is verified by unit tests (synthetic pictures from our own renderer) and CI only.

The design is `builds/song-tap-code-design/RING-CODE-SPEC.md` (approved 2026-11-20). Order of ways to beam: Bluetooth tap, ring code, the plain QR last ("Use QR code instead" after about 6 s of failed ring scanning or when the camera cannot run the scanner).

## How the app side uses it (next milestone)

- Sender: `RingCodePayloads.encodeSlots(videoId, RingCodePayloads.bucketOf(nowMs), random)` gives 200 bits (0 = small dot, 1 = big dot, index = slot id). Draw with `RingCodeLayout` geometry and `RingCodeStyle.palette(dynamicPrimary)`; animate with `RingCodeTimeline`. A song with no videoId cannot use the ring code (QR path).
- Receiver: one `RingScanner` on the analysis thread. Per frame build `RingFrame(width, height, lumaPlane)`, optionally with a coarse hue map (`RingHue.orangeness(U, V)` per sample, 0..255); the hue map is only a tie-breaker, the scanner works without it. Feed each result to a `RingScanAccumulator` (3 equal decodes, no more than 2 s apart); when it returns a payload, check `RingCodePayloads.freshness(bucket, nowMs)` and resolve the video id.
- `scanner.diagnostics` (centre, outline radius, start dot found, matched dots, residual, per-slot confidence, per-slot bits, RS corrections, erasures used, scan micros) is what the Developer mode scan screen shows.
- Frames are downscaled inside the scanner to at most 800 px on the long side (`RingScanner(maxSide)`); the app should still skip frames (analyse one in two or three) so it never starves the UI. The scanner reuses its image buffers; a scan allocates only small arrays (blob lists, match tables).

## Deviations from RING-CODE-SPEC.md

1. **Byte map**: byte b owns the eight neighbouring slots 8b..8b+7 (MSB first), not "j, j+25, ...". Every ring size is a multiple of 8, so a byte is a run on one ring. The spec's scatter makes a smudge touch all 25 bytes by one bit each (more than 14 erasures can mend); the neighbour map keeps a run of neighbours to a few bytes and a 72 degree wedge across all five rings to at most 14. `RingCoreTest` shows the difference.
2. **Payload**: the 22-bit tag is 6 bits of minute bucket + 8 random + an 8-bit CRC-8 (spec: 16 random). The CRC rejects the rare erasure-heavy miscorrection. Freshness: the bucket may be the receiver's current minute, one of the two before or the one after (2 to 3 minutes of life, a clock up to a minute behind is fine).
3. **Geometry** (changed from the first ring-code commit, so `ring-layout.jsonl` changed): the art disc is radius 280 (spec 300) with a light gap, and a dark outline ring 305..330 around it. The scanner finds the code by that outline (a closed ellipse whatever the artwork holds; still an arc when a smudge hides part of it). The start dot sits at 12 o'clock at radius 895, one ring pitch outside the outer ring (spec: on the outer ring's slot 0), so it never takes a data slot.
4. **Idle motion**: the whole code sways as one piece (1.32 rad one way in 6 s, eased, then back, then the other way) instead of rings turning against each other, so the scanner always has one start dot to read from. The GIF's alternating rings are not reproduced.
5. **Scanning method**: not "circle detection plus hue test". The scanner thresholds against a local mean, labels dark blobs, takes the large round blob as the outline, fits its ellipse (moments, or an arc fit when part is hidden), finds the start dot as the dot-sized blob beyond the outer ring (hue only breaks ties; a device colour that is itself orange cannot hide it), matches the 200 slot positions to dot blobs ring by ring while refining an affine then a homography fit, measures each dot's dark mass against the plate level right around it, decides big or small per ring with two-means, and Reed-Solomon decodes with the least certain bytes flagged as erasures (0, 3, 5, 7, 10 tried in turn). If the start dot is hidden or wrong it tries the eight turns that fit the dot positions (they are eight-fold symmetric). Several outline candidates (moments fit and arc fit) are tried, best first.
6. The erasure ladder stops at 10: 12 only helped past a 25 percent smudge and raises the CRC's miss rate to about 1 in 7000 per frame.

## What the tests show (synthetic, this JVM)

Success rates of the scanner on pictures from our own renderer (360 x 360 frame, plate 260 px across unless said; each row a fresh random code):

| Impairment | Result |
|---|---|
| rotation 0..360, every 3 degrees (120 scenes) | 120 / 120 |
| tilt 5..30 degrees, 8 axes, random rotation (48) | 48 / 48 |
| blur sigma 0.5, 1, 1.5 px (36) | 36 / 36; sigma 1.75 10 / 10; **sigma 2.0 0 / 10** (the 3 px outline ring melts) |
| blur sigma 1, 2, 3 px on a 520 px plate (24) | 24 / 24; sigma 4 px: 2 / 6 |
| noise sigma 4..16 levels (40) | 40 / 40; 24, 32, 48: 10 / 10; 64: 7 / 10 |
| smudge over 10, 15, 20 percent of the slots, grey or plate-coloured (3 x 40) | 40 / 40 each |
| smudge 25, 30, 35, 40 percent | 10, 8, 5, 2 of 10 (the ladder stops at 10 erasures; 12 would give 10, 9, 9, 4) |
| glare, 1 to 2 patches of 25..55 px (60) | 51 / 60 (85 percent); the misses are glare over the outline or over more than 20 percent of the slots |
| low contrast, 0.5 and 0.35 of full | 16 / 16; 0.25: 8 / 10; 0.18: 0 / 10 |
| plate size | 260, 200, 160, 130 px wide: 10 / 10; 100 px: 0 / 10 |
| tilt past 30 | 40, 50: 10 / 10; 60: 9 / 10; 70: 0 / 10 |
| clutter, five art kinds (dark, light, stripes, texture, orange texture), off-centre plate, noise (80) | 79 / 80 (one `no_plate`) |
| start dot hidden (24) | 24 / 24 |
| 40 random device-colour palettes (dark and pale), blur, noise, tilt | 39 / 40 |

**Worst case that still read**: tilt 60 degrees, noise sigma 48, smudge 35 percent (9 / 10 with 12 erasures, 5 / 10 with 10), contrast 0.25, blur 1.75 px at 260 px, a plate 130 px wide.

**Never wrong**: 400 random images (noise, checkerboards, discs, near-code pictures): 0 decoded. 240 codes with random smudges and glare of any size, many far past repairable: 89 read right, 151 not read, **0 read wrong**. The accumulator needs 3 equal decodes in a row.

Speed on the dev machine's JVM (warm, one core): about 7 ms for a 360 x 360 frame, about 10 ms for 1280 x 720 (downscaled to 800 px inside). A phone core will be several times slower; the app side decides the frame skipping.

## Unverified (needs real phones)

- iOS dots use the app accent and a lighter tint of it (RING-CODE-SPEC.md); the code sits on a flat plate, never on Liquid Glass.

# R2: the code on the screen (renderer, camera scanner, flow, diagnostics)

Branch `everything`. Everything below runs only on the phone's side of the line the core drew: Compose drawing, CameraX, the Song Tap controller and the Developer mode screen. **Nothing here has run on a phone**: it is verified by unit tests over fakes, compilation and CI.

## What the screen does now

Order of ways to beam: 1. the Bluetooth tap (unchanged), 2. the ring code, 3. the QR code, last.

- **Sender**: "Use a code instead" shows the Pixl ring code in place of the big artwork (the playing song's art is the disc in the middle). The code is made again with a fresh tag every 60 s (`RingSendRules.CODE_LIFE_MS`) and when the song changes. "Use QR code instead" appears on the sender after the code has been up for 6 s (a sender cannot see the receiver's scan, so "up for 6 s" stands in for "failed for 6 s"; deviation 1). The QR is never shown beside the ring code. A song with no video id (never matched) goes straight to the QR with one line: "This song has no video yet, so it can only be shared with a QR code."
- **Receiver**: "Scan a code instead" opens the camera for the ring code. "Use QR code instead" appears only when the scan has run 6 s without reading a code, or at once when the phone has no camera / CameraX will not start / the average scan is slower than 450 ms (the scanner is too slow). A tag that is too old or too new, or a failed lookup, also offers it. The old QR scanner (zxing) opens only from that button and has a "Back to the Song Tap code" button.
- **On a decode** (three equal fresh reads in a row): the receiver looks the song up from the video id (`InnerTubeClient.getQueue`, the same `music/get_queue` call the brain uses; needs the internet; 10 s timeout) and then the usual `OfferReceived` happens: first-beam Add / Not now, rate limits (3 s gap, same video 60 s, ...), save through the library, Undo, the receiver beam card. A lookup that fails says so and offers the QR (the QR carries the name and works offline); the same code is left alone for 3 s, then may be tried again.
- **Guards** (`RingCodeGuard`): freshness (this minute, two minutes back, one ahead) and replay (the same video and tag is taken once in 5 minutes; a failed lookup does not count as taken).

## The renderer (`RingCodeView`)

Colours: dots = the device colour (Material You primary for light or dark on API 31+, the app's primary on API 30) through `RingCodeStyle.palette` (darkened toward tone 30 only as far as 7:1 needs); plate = tone 95 of the same hue in both modes; round dots; the orange start dot; the outline ring in the dot colour.

Performance: one geometry per size (`drawWithCache`): the 200 dot centres as two flat float arrays (big and small), drawn at rest with two `drawRawPoints` calls and a handful of shapes; `RingCodeTimeline.frameInto` is read inside the draw block and the art's `graphicsLayer` block (no recomposition, no allocation); during the beam each dot is its own `drawCircle` (200 for 2 s). Idle clock ticks at about 30 fps and not at all with animations off; no blur anywhere (the glow is one radial brush). The beam: dots peel off the outer ring first and spiral into the art (a turn of 0.32), the plate and outline fade, the art pulses, lifts to 0.38 and leaves through the top, then the "Sent" pill. Reduce Motion (animator scale 0): nothing sways and the beam is the 150 ms cross-fade of the timeline.

## The scanner on the phone (`RingCodeCamera`)

CameraX `Preview` + `ImageAnalysis` (1280 x 720 preferred, `STRATEGY_KEEP_ONLY_LATEST`), one daemon thread at below-normal priority, bound to the lifecycle (leaving the screen or the app unbinds it; the Receive pane also ends its scan session on pause). `RingScanPacer`: at most one scan per 110 ms and a wait of twice the last scan's length when scans are slow. `RingFrameBuilder` copies the luma plane without padding and builds the hue map from U and V (one sample per 2 x 2 pixels, `RingHue.orangeness`); arrays are reused. The scanner downscales to 800 px itself. Results go to `SongTapStateHolder.ringSink`, which feeds `RingReceiveFlow`. Camera permission: the same flow as before (asked the first time the listener opens a scanner).

**zxing**: kept, for the last-resort QR only (reading and drawing). **No new dependency** was added in R2; CameraX 1.6.2 was already in.

## Developer mode > Ring code diagnostics

Settings > Song Tap, with Developer mode on. A live view of what the scanner sees (grey, upright; this is the analysed frame, not the camera preview, so the overlay lines up exactly) with the plate's outline circle (green), the art circle (cyan), the plate's reach (faint) and the orange start dot; frames per second, scans per second, last scan time, dots matched of 200, outline candidates, Reed-Solomon fixes and erasures, residual; the 200 slots drawn as the plate lays them out, coloured by confidence (green clear, amber weak, red unknown); the last 20 results with "Copy log" (device, numbers, results); and the renderer at this phone's colour in light and dark mode with hex values, contrast and tone, and "Play the beam". It does not arm Song Tap: scanning there never saves a song.

## Deviations from the R2 brief and the spec

1. The sender's "Use QR code instead" appears 6 s after the ring code is shown, not after a failed scan (it cannot know).
2. The diagnostics picture is the analysed luma frame, not the live preview.
3. The ring beam animation is played on the sender when a beam starts there; over the code route the sender never learns that the receiver scanned (nothing travels back), so in practice it is seen in Developer mode's "Play the beam" and on any Bluetooth beam. The receiver's beam card is unchanged.
4. Resolving a ring code needs the internet (spec). The card's art comes from the lookup, which can be a different cover than the sender's.
5. "Camera cannot run the scanner": no camera feature, CameraX bind failure, or scanner too slow. When the camera itself is missing the QR button leads to a scanner that also needs a camera; it is offered because the order of options says so.

## How to test with two phones

1. Both phones: Settings > Song Tap on; Developer mode on one for the diagnostics.
2. Phone A: play a song that has been played before (it has a video), open Song Tap, Send, "Use a code instead": the ring code with the song's art in the middle. Phone B: Receive, "Scan a code instead", allow the camera, point it at A at arm's length in a bright room. B asks Add / Not now the first time, then "Added to your library" with Undo.
3. Try dim light, a tilted phone, a smudged screen, from further away, with A's brightness low: watch the Ring code diagnostics on B (Settings > Song Tap > Ring code diagnostics) for the slot confidence and the Reed-Solomon fixes; "Copy log" and send it back.
4. Leave B pointing at a wall for 6 s: "Use QR code instead" appears. On A wait 6 s: the same button appears; tap it on both: the QR route works as before.
5. A song never played (no video): A shows the QR with the line saying why.
6. Take the same code twice: the second is refused ("You already took that code").
7. Turn A's clock a few minutes back or forward: B says the code ran out or to check the date and time, and offers the QR.
8. Developer settings > animator duration scale off: the ring code does not sway and the beam is a cross-fade.
