## Diagnostics log (Settings > About > Support > Diagnostics)

What it records, to `noBackupFilesDir/diagnostics/` (never backed up), two files rotating at 500 KB each, so at most 1 MB:

- Every Timber WARN/ERROR/WTF line (`DiagnosticsTree`, planted in debug and release).
- Explicit events via `DiagnosticsLog.event(tag, message)` (INFO survives R8; `Timber.i` does not):
  app start (version, commit, build date, device); Spotify signed-in state at start and on change;
  every WorkManager job RUNNING / SUCCEEDED / FAILED / CANCELLED / retry, with the worker class, attempt and numeric output
  counts only (so import start/finish/failed show up as `SpotifySyncWorker ...`); every failed HTTP call (status >= 400 or an
  exception class, plus Retry-After) as `METHOD host/path -> status` with no query, headers or body, on the default,
  lyrics ("fast") and YouTube OkHttp clients (Spotify's Retrofit clients derive from the default one); playback audio
  started/stopped and playback failures (error code name, cause chain, URI without query, track as an opaque id);
  lyrics lookups (track id, found/none, source, failure class).
- Uncaught exceptions: a default `UncaughtExceptionHandler` written after `CrashHandler`, which logs the stack, then delegates
  to the previous handler (the crash dialog keeps working).
- `ActivityManager.getHistoricalProcessExitReasons` at startup (new entries only) and in the shared report.

Redaction (`DiagnosticsRedactor`, applied to every line and stack trace): URLs keep scheme/host/path only; Bearer tokens,
`token=`/`key=`/`code=` pairs (short numeric values such as `code=403` stay), JWTs, e-mails and any 32+ char letter+digit
string become `<redacted>`/`<email>`. Titles and artists are never written on purpose; `opaqueId()` gives `#a1b2c3` instead,
and titles seen by the lyrics lookup are registered so a third-party log line that mentions one is rewritten too.

Screen: build version, commit sha, build date, whether Spotify sign-in is configured, device info, last exits, the last 40
log lines, Share logs (a `.txt` through the existing FileProvider and the share sheet) and Clear logs.

Commit sha: `GITHUB_SHA` (first 7) in CI, else `git rev-parse --short HEAD`, else `unknown`; date is the UTC build date.

How to use: reproduce the problem, open Settings > About > Diagnostics > Share logs, send the file. To add a breadcrumb in
code: `DiagnosticsLog.event("Tag", "message with no personal data")` (do not use `Timber.i`).

Unit tests: `DiagnosticsRedactorTest`, `RingBufferLogTest` (cap, rotation, order, truncation, clear, threads),
`DiagnosticsReportTest`.

## Integration notes for the three parallel agents

My edits in files they own are one or two lines each, so conflicts should be trivial; re-add if they get lost in a merge:

- `data/service/PlaybackActivityTracker.kt`: logs "audio started/stopped" inside `setPlaybackActive`.
- `data/service/PlaybackErrorReporter.kt`: logs the failure inside `report`.
- `data/repository/LyricsRepositoryImpl.kt` `getLyrics`: `DiagnosticsLog.event("Lyrics", ...)` at the memory-cache, stored, found,
  failed-source and not-found exits, plus `DiagnosticsRedactor.registerSensitive(...)` at the top.
- `di/AppModule.kt`: `.addInterceptor(DiagnosticsHttpInterceptor)` on the three OkHttp providers.
- `PixelPlayApplication.kt`: `DiagnosticsLog.init`, `DiagnosticsTree`, the app-start event and the two watchers.

The import agent should log its own stages with `DiagnosticsLog.event("SpotifyImport", "playlists=12 tracks=1500 http=429")`
(counts and status codes only).

## Plain checks (on the phone)

1. Install the CI debug APK, open Settings > About: a "Support" section with a Diagnostics card appears.
2. Diagnostics shows the version, a 7-char commit sha (not `unknown` for CI builds) and today's build date.
3. Open it again after a Spotify sign-in attempt and after an import: lines for `Spotify`, `Work` and (on a failure) `Http` appear.
4. Share logs opens the share sheet with `pixlaudio-diagnostics.txt`; open it: no tokens, no `?query` strings, no song titles.
5. Clear logs empties the list.
6. Fresh install, onboarding: deny notifications twice, you can still press Next/Finish.
7. Release build: the same file has content (WARN+ and events), proving the stripped-INFO workaround.
